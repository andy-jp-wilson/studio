# Studio replan: closing the gap between design and code

Status: **draft for approval** (2026-10-20, revised the same day). Nothing in this plan is built yet.

## The goal, restated

Studio makes Claude Code a clearer, calmer and safer place for designers to work. It connects Claude Code to Figma and to a team's **design system and/or component library, in whatever form they come in**, so design and development share one source of truth instead of passing pictures back and forth.

Studio is for **any design team**. It names no particular company, team or design system. It only mentions a team's own design system once that team has connected it (through `/setup` or a team preset).

Two halves, in this order of importance:

1. **The bridge.** Moving work between Figma and a working prototype, in both directions, using the team's design system and component library, so what developers receive is close to what they'll build.
2. **The comfort.** A clear, calm, safe, plain-language Claude Code: friendly words, snapshots, save points, the band and panel.

Until now most of the effort went into the comfort. This plan shifts it to the bridge.

## Principles (unchanged)

- Clear first, then calm: plain language, one step at a time, nothing hidden; teach, then step back.
- Always safe to undo.
- Work stays on this computer unless the person says otherwise.
- Show what changed in design terms, not code.

New:
- **The team's design system is the shared language.** Prototypes use its components and tokens (the named colours, spacing and type that code and Figma share), never lookalikes.
- **The Claude app first.** Most designers will use the Code tab in the Claude app, so it's the main place Studio is designed and tested for. The terminal stays fully supported.
- **Explain the tools, not just the steps.** Designers may wonder why they're in Claude Code at all. Studio says plainly what each Claude tool is for and when to use which.
- **Works with any team.** No company, team or design system is built in. Whatever a team connects is what Studio uses and names.
- **Editable, not pictures.** Anything Studio puts in Figma should be real layers a designer can work with.
- **Seen before built on.** Each phase ends with the designer trying it in the app before the next one starts.

## Keep, rework, pause

**Keep as is:** the Studio voice and words, snapshots and "go back", save points and explorations, the upload guardrail, `/version`.

**Rework:**
- **Make Studio team-neutral.** Today `/setup` asks "Is this the Acme Design System?", and `/handover`'s developer pack and Figma page say "Acme Design System, our design system" and have "Acme Design System reference" sections. These become "your design system", using whatever name the team connected, or a plain "Design system: not connected yet" when there's none. An example in `/setup` also names a company; it becomes a neutral one.
- **`/setup`'s design system step** grows to accept a design system and/or component library in any form (see Phase B), not only a Figma file.
- **The tagline** is now "Clearer, calmer Claude Code for designers" (decided 2026-10-20, applied in Studio 0.2.6).
- **Send to Figma** becomes `/to-figma`: editable Figma frames built from the running prototype, not a screenshot.
- **`/handover`**: its Figma page uses editable frames and points to the team's design system components, not pictures or repeated values.
- **Journey stages**: tie Explore, Refine and Build to where the work is in a design journey (for example "in Figma", "in the prototype", "in review"), not to save-point counts.
- **The Figma file of Studio**: decide whether to update pages 00 to 05, or treat what's built as the reference from now on.

**Pause:** further band and welcome polish, the terminal look and status line, teaching that fades, `/learn` and `/explain`.

## The phases

Each phase ends with the designer trying it in the Claude app, and a pause for approval.

### Phase A: look and align

- Go through Studio in the app together, using `plans/phase-3-test-checklist.md` and `plans/setup-test-checklist.md`. Note everything that feels off: the look, the words, the steps.
- Write **"A day with Studio"**: one page describing a designer's day from opening a project to handing over, step by step. This becomes the target experience everything else is checked against.
- Answer the open questions below.
- Make Studio team-neutral (see Rework).
- **Which Claude for what.** Short, plain guidance on Claude (chat), Claude Design and Claude Code: what each is good at, when a designer would use one rather than another, and why Studio lives in Claude Code (it works on real files and a running prototype, and connects to Figma and the design system). Checked against Anthropic's current docs before writing, since these products change. It goes in `/guide`, the start of `/setup`, and "A day with Studio".
- Fix only what blocks the next phases.

Done when: the designer has seen everything that's built, and "A day with Studio" is approved.

### Phase B: the design system first

A team's design system and component library can come in many forms, often several at once. Studio should accept whichever the team has:

- a **Figma library** (components, styles and variables)
- a **coded component library**, e.g. a package developers install, or a folder in a repository
- a **tokens file** (colours, spacing and type as data)
- a **documentation site**, e.g. Storybook or a design system website
- none yet

Work:
- `/setup` asks what the team has, in plain words, and accepts any mix of the above (with a team preset so designers don't need to know the details).
- Pull tokens into the prototype from whatever source exists (Figma variables or a tokens file), so colours, spacing and type match by name.
- If there's a coded component library, build prototypes with it. If not, build a small set of matching components from the Figma library, and record which is which (Code Connect is Figma's way of linking a Figma component to its code).
- With no design system at all, Studio still works, and says plainly that prototypes use simple defaults.

Done when: a new prototype screen uses the team's tokens (and components, where they exist), and the designer can see that it matches Figma. Tested with at least two kinds of setup, e.g. Figma library only, and Figma library plus coded components.

### Phase C: Figma to prototype (`/from-figma`)

- Point at a Figma frame (a link, or the current selection) and Studio builds it as a working screen in `prototype/`, using the team's design system.
- Studio says what it matched to the design system and what it couldn't, in plain words.
- Ends with `/preview`, so the designer sees it running.

Done when: a real frame from the designer's file becomes a working screen they're happy with, in a few minutes.

### Phase D: prototype to Figma (`/to-figma`)

- Turn the running screen into editable Figma frames in the project's Figma file (from `/setup`), using the design system's Figma components where they match.
- Replaces the panel's Send to Figma picture.
- Always asks before writing to Figma.

Done when: a screen made in code appears in Figma as layers the designer can edit.

### Phase E: the review loop

- Bring comments from the Figma file back to Claude as a list of changes, in plain words, for the designer to approve.
- Make the changes in the prototype, then offer to update the Figma frames.

Done when: one round of review (comment in Figma, change in the prototype, updated in Figma) works without leaving the flow.

### Phase F: hand over and share

- Rework `/handover` around the team's design system and editable frames.
- Ask developers what they most want to receive, and shape the developer pack to fit.
- The remaining guardrails.
- Put Studio on the team's GitHub so other designers can install it, and test `/version` updates for real.

Done when: a second designer installs Studio and completes "A day with Studio".

### Later

Terminal look and status line, teaching that fades, `/learn`, `/explain`, `/from-design` (Claude Design handoff), more polish on the band and panel.

## Open questions

1. **Your own design system, as the first test case:** what forms does it come in (Figma library, coded components, tokens, documentation)? It's the first real example, while Studio stays team-neutral.
2. **What developers want:** what do they most need from designers today, and in what form?
3. **"Unrefined":** what felt off when you first looked: the look, the words, the steps, or something else?
4. **The other guardrails:** what are they?
5. **The Figma file of Studio:** update it, or treat what's built as the reference?

## Changes to the original brief

- The three journeys on Figma page 04 move from "later" to the centre of the plan (Phases C to E).
- "Terminal first" becomes **the Claude app first**; the terminal stays fully supported (decided 2026-10-20).
- Studio is team-neutral: no company, team or design system is named unless a team connects it.
- "Calm" stays, but alongside "clear" (and "safe"); clarity comes first.
- Polish, the terminal look and teaching that fades move to "later".
