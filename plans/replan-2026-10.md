# Studio replan: closing the gap between design and code

Status: **approved** (2026-10-20), revised the same day after the team's answers (Figma first, prototypes optional). Phase A in progress.

## The goal, restated

Studio makes Claude Code a clearer, calmer and safer place for designers to work. It connects Claude Code to Figma and to a team's **design system and/or component library, in whatever form they come in**, so design and development share one source of truth, and developers get designs that are reliable, easy to understand and complete.

Studio is for **any design team**. It names no particular company, team or design system. It only mentions a team's own design system once that team has connected it (through `/setup` or the team's settings).

Today's reality for the first team: designers work **in Figma first**, using library components to mock up flows for the business, other designers and stakeholders. HTML/CSS prototypes are the next step towards code, but **optional** for now. So Studio has to be useful to a designer who never makes a prototype.

Three parts, in this order of importance:

1. **Help in Figma.** Checking designs against the design system, capturing interaction design (states and behaviour), and handing over clearly.
2. **The bridge to code.** Optional prototypes in both directions, built from the team's design system and component library.
3. **The comfort.** A clear, calm, safe, plain-language Claude Code: friendly words, snapshots, save points, the band and panel, and learning developer words over time.

## Principles

- Clear first, then calm: plain language, one step at a time, nothing hidden; teach, then step back.
- Always safe to undo.
- Work stays on this computer unless the person says otherwise.
- Show what changed in design terms, not code.
- **The team's design system is the shared language.** Checks, handovers and prototypes use its components and tokens (the named colours, spacing and type that code and Figma share), never lookalikes.
- **Figma first; prototypes optional.**
- **The Claude app first.** Most designers will use the Code tab in the Claude app, so it's the main place Studio is designed and tested for. The terminal stays fully supported.
- **Explain the tools, not just the steps.** Designers may wonder why they're in Claude Code at all. Studio says plainly what each Claude tool is for and when to use which.
- **Works with any team.** No company, team or design system is built in. Whatever a team connects is what Studio uses and names.
- **Editable, not pictures.** Anything Studio puts in Figma should be real layers a designer can work with.
- **Protect what's shared.** The design system files and other people's Figma work can't be changed by accident.
- **Seen before built on.** Each phase ends with the designer trying it in the app before the next one starts.

## Keep, rework, pause, park

**Keep as is:** the Studio voice and words, snapshots and "go back", save points and explorations, the upload guardrail, `/version`.

**Rework:**
- **Make Studio team-neutral.** Today `/setup` asks "Is this the Acme Design System?", and `/handover`'s developer pack and Figma page say "Acme Design System, our design system" and have "Acme Design System reference" sections. These become "your design system", using whatever name the team connected, or a plain "Design system: not connected yet" when there's none. An example in `/setup` also names a company; it becomes a neutral one.
- **`/setup`** asks which design system this project uses (a team can have more than one, e.g. a new one and an older one), and accepts a design system and/or component library in any form (see Phase B).
- **Studio's look** moves away from Claude's: based on the connected design system's colours and type where there is one, and a neutral default where there isn't. Explored at the walkthrough.
- **Send to Figma** becomes `/to-figma`: editable Figma frames, not a screenshot.
- **`/handover`**: done in part (2026-10-20, Studio 0.2.8): one handover per project, updated each time, with the project's Figma file link at the top and earlier changelogs kept. Still to do: a Figma page that's ready for developers, with components, states and behaviour, pointing to the design system and component library (e.g. Storybook entries), not pictures or repeated values.
- **Journey stages**: tie Explore, Refine and Build to where the work is (for example "in Figma", "in review", "handed over"), not to save-point counts.

**Pause:** further band and welcome polish, the terminal look and status line.

**Park (separate projects or later):**
- **Accessibility checks** (contrast, text size, tap targets): a separate project.
- **Behaviour across screen sizes:** explore later.
- **Learning HTML and CSS properly:** a separate project. Studio keeps a light bridge: ask "what does this part of the prototype do?" and get a plain answer.
- **Figma template:** the team is building one; it slots into `/setup` when ready.
- **Measuring whether it's working:** checked by hand, not built into Studio.

## Guardrails

Three groups, so designers are protected without being asked questions all the time.

**1. Never, unless the team turns it on**
- **Changing a design system file.** Every design system the project or team has connected is read-only to Studio. Reading is always fine. This covers overwriting library components.
- **Writing outside the allowed Figma places.** The company may share one Figma organisation, so the team lists the Figma teams or folders Studio may write to. Studio only writes to the project's own Figma file (from `/setup`), and only creates new files in an allowed place.
- **Uploading anywhere but the team's places** (already built).

**2. Ask first, saying what will happen in plain words**
- Deleting files, or throwing away unsaved changes.
- Writing to the project's Figma file.
- Replacing or deleting frames or pages in Figma, e.g. "This deletes 3 screens from the Sign-up page. Studio can't bring them back."
- Installing software.
- Uploading.

**3. Free**
- Anything inside the project that a snapshot can undo.

**To explore later:** working on **Figma branches** when editing shared files, and starting new files from **the team's template** (once it exists). Both depend on what the Figma connection can do; to be checked before promising.

**How they're enforced:** like the upload rule, Studio checks each action before it runs, including every Figma action, so they don't depend on Claude remembering. To check: whether the Figma connection can tell which folder an existing file is in. If it can't, Studio checks the place when a file is created, and only trusts files linked through `/setup`.

**Consistency check:** designs don't contain sensitive information, but Studio's design check also looks for anything that seems out of place (e.g. real-looking personal details) and flags it the same way everywhere in the project.

## Team settings: how they reach each designer

Studio is a plugin each designer installs, so there's no single switch for the whole team. Three ways the team's settings (allowed Figma places, upload places, design systems, template) can reach everyone:

1. **A setup guide** (for now): a short Markdown file the team shares. A designer opens it with Studio and Claude walks them through entering the team's settings. Simple, works today, relies on each person.
2. **Studio's team copy** (later): when the team installs Studio from its own GitHub, the team's settings can live in that copy, so everyone gets them on install and on each update.
3. **Company-managed settings** (if IT wants it): Claude Code supports settings an IT team places on every computer, which people can't change. Whether the company uses this is a question for IT.

Phase A starts with option 1.

## The phases

Each phase ends with the designer trying it in the Claude app, and a pause for approval.

### Phase A: look, align and discover

- **Walkthrough.** Go through Studio in the app together, using `plans/phase-3-test-checklist.md` and `plans/setup-test-checklist.md`. Note everything that feels off, including the look.
- **Discovery.** Short questions for two or three designers and one or two developers: `plans/discovery-questions.md`. Their answers name the real problems.
- **"A day with Studio".** One page describing a designer's day from opening a project to handing over, Figma first. The target experience everything else is checked against.
- **Which Claude for what.** Short, plain guidance on Claude (chat), Claude Design and Claude Code: what each is good at, when to use which, and why Studio lives in Claude Code. Checked against Anthropic's current information first. Goes in `/guide`, the start of `/setup`, and "A day with Studio". Done in `/guide` and `/setup` 2026-10-20 (Studio 0.2.9); sources in `plans/which-claude-sources.md`.
- **Team-neutral.** Remove the built-in names (see Rework). Done 2026-10-20, Studio 0.2.7.
- **Team setup guide** (draft): the Markdown file from "Team settings", option 1. Drafted 2026-10-20 (Studio 0.2.11): `plugin/team/studio-team-setup.md`, with `bin/studio-team`; `/setup` now offers the team's design systems as a choice (a small piece of Phase B).

Done when: the designer has seen everything that's built, the discovery answers are in, and "A day with Studio" is approved.

### Phase B: the design system

A team's design system and component library can come in many forms, often several at once: a **Figma library**, a **coded component library** (e.g. Storybook, or a package developers install), a **tokens file**, a **documentation site**, or none yet. The first team has a Figma library and Storybook, plus an older design system still in use.

- `/setup` asks which design system the project uses, from the ones the team has connected, and remembers it. The project can switch later.
- Studio reads the chosen design system's Figma library: components, styles and variables.
- Link Figma components to their Storybook entries where they match (Code Connect is Figma's way of linking a Figma component to its code), so handovers can point developers to the real code.
- With no design system at all, Studio still works and says so plainly.

Done when: a project knows its design system, and Studio can name the library components used on a screen and where each lives in Storybook.

### Phase C: help in Figma

- **Design check:** look over a flow and flag, in plain words, detached components, colours or text styles not from the library, spacing that doesn't match, missing states (hover, focus, disabled, error), and anything that looks out of place.
- **Interaction notes:** help the designer capture behaviour (what happens on hover and click, loading, errors) as notes on the frames, in a consistent format developers can rely on.
- **Learning developer words:** the words developers use for these things (states, props, variants, tokens) introduced alongside the friendly ones, more over time.

Done when: the designer runs a check on a real flow, fixes what it found, and adds interaction notes, in a few minutes.

### Phase D: Figma guardrails

- Design system files protected from changes.
- Writing only to the project's Figma file, and new files only in allowed places.
- Asking first before replacing or deleting frames or pages.
- Explore Figma branches and templates.

Done when: trying to change a library component, or to write to another team's file, is stopped with a clear explanation.

### Phase E: hand over

- Rework `/handover` into a ready-for-developers Figma page: each screen's components, their states and behaviour, linked to Storybook.
- Shape it with the developers' discovery answers.

Done when: a developer reads a handover and says it has what they need.

### Phase F: prototypes (optional)

- `/from-figma`: a Figma frame becomes a working HTML/CSS screen, using the design system's tokens and components.
- `/to-figma`: a working screen becomes editable Figma frames.
- The review loop: Figma comments come back as changes; updated screens go back to Figma.
- CSS for developers comes from the working prototype.

Done when: one screen goes from Figma to prototype and back, editable at each end.

### Phase G: share

- Put Studio on the team's GitHub so other designers can install it, with the team's settings in it (option 2), and test `/version` updates for real.

Done when: a second designer installs Studio and completes "A day with Studio".

### Later

Terminal look and status line, teaching that fades (beyond developer words), `/learn`, `/explain`, `/from-design` (Claude Design handoff), more polish on the band and panel, and the parked items above.

## Answers so far (2026-10-20)

1. **Design system:** for designers, a **Figma library**; **Storybook** acts as the coded component library. There's also an **older design system** still in use, so each project must confirm which one it uses. Workflow is **Figma first**; HTML/CSS prototypes are the planned bridge but **optional** for now.
2. **What developers want:** designs that are **reliable, easy to understand and consistent** with what's expected, with the key information in, **especially interaction design** (hover states, behaviour). CSS too, which can come from the prototype.
3. **"Unrefined":** it isn't quite solving the problems yet, and the problems aren't fully known (hence discovery). The workflow is still unclear. The **look is too close to Claude's**; perhaps base it on the team's design system. Revisit at the walkthrough.
4. **Guardrails:** nothing too destructive without realising it; some things not by default at all, e.g. **overwriting design system components**. The company shares **one Figma organisation**, so writing must be limited to particular teams or folders. Possibly **Figma branches** and **the right template**, to explore.
5. **Studio's Figma file:** completely redo, design included, once the above is clearer.
6. **Learning:** more on **developer terminology**. Learning HTML and CSS is likely a separate project.
7. **Parked:** accessibility (separate project), screen sizes (later), measuring success (by hand). Sensitive information isn't used, but a consistency check runs through the project.
8. **Team settings:** for now, a Markdown setup guide each designer uses.

## Changes to the original brief

- Figma first: help in Figma comes before prototypes, which become optional.
- The three journeys on Figma page 04 still matter, but as Phase F.
- "Terminal first" becomes **the Claude app first**; the terminal stays fully supported.
- Studio is team-neutral: no company, team or design system is named unless a team connects it.
- "Calm" stays, but alongside "clear" (and "safe"); clarity comes first.
- Teaching starts with developer words; the rest of "teaching that fades" stays later.
